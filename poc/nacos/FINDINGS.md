1. ⚠️ Nacos 2.4.3 不提供任何默认账号（部署阻断项）
--------------------------------------------------

**观测**：

- `conf/derby-schema.sql` 只 `CREATE TABLE users / roles / permissions`，**全文零条 `INSERT`**。
- `conf/mysql-schema.sql`（210 行）**同样零条 `INSERT`**。
- 开启鉴权后，`POST /v1/auth/login` 返回 `caused: User nacos not found;`。

**即：无论用 derby 还是 MySQL，Nacos 2.4.3 都不会自动创建 `nacos/nacos`。**

**更麻烦的是无法自举**：`application.properties:42` 把 `/v1/auth/**` 放进 `nacos.security.ignore.urls`，
按理建号接口应免鉴权；但实测 `POST /v1/auth/users -d username=nacos&password=nacos` 返回
`500 Server failed, User nacos not found`，服务端堆栈为
`org.springframework.security.core.userdetails.UsernameNotFoundException: User nacos not found`。
**建号接口自己也要求先存在一个用户 → 鸡生蛋。**

**影响**：批次 1 不能只写「开鉴权」，必须包含**显式初始化管理员**这一步，否则组件起得来、却登不进。

**✅ 解法（已实测）**：端点写作 `/v1/auth/users/admin`（**路径参数是字面量 `admin`，不是用户名**）。

```
POST /nacos/v1/auth/users/admin   -d "password=<新密码>"
```

调用后的响应**回显了明文密码**（`{"username":"nacos","password":"<此处原文是明文密码，已脱敏>"}`）——这是 Nacos 该接口的行为，
虽不理想但只发生在初始化那一刻；**注意别把响应体打进日志**。

> 🔒 本文档入库前已脱敏：原文照抄了实测时的密码明文，按「凭据不落公开仓库」改为占位符。
> 该密码属一次性 PoC 实例（容器已 `compose down`），**不影响本条结论**——要点是「接口会回显」这个行为。

随后 `POST /v1/auth/login` 成功，返回 `globalAdmin:true` + `accessToken`。

**这个解是 Nacos 自己给的**：用老写法 `POST /v1/auth/users?username=nacos` 时，服务端返回
`409`，响应体明写：

> `User 'nacos' is default admin user. Please use '/nacos/v1/auth/users/admin' API to init 'nacos' users.`

即：`nacos` 是**受保护的内置用户名**，常规建号接口会拒绝它，必须走专门的初始化接口。

> **归因仍属推测**：我不能断言这是「2.4.3 的 bug」还是「2.2.0 起的刻意安全收紧」——**没查过版本变更说明**。
> 但「内置名 `nacos` 被专门拦下并要求走 `/admin` 初始化接口」这个**行为**本身，指向刻意设计而非疏漏。

**✅ auth 开启时已验证（补测通过）**：以 `POC_AUTH_ENABLE=true` 重启（derby 被 `down` 清空，即全新实例），
无 token 调 `/v1/auth/users/admin` **成功**建成管理员，随后登录成功；
同时无 token 读配置返回 **403**，证明鉴权确实在强制。

→ **批次 1 的初始化步骤**：启动 Nacos（鉴权已开）→ 调一次 `/v1/auth/users/admin` 设置管理员密码 → 完成。
**不需要**「先关鉴权建号再开」那种绕法。

**🔴 但由此暴露一个安全事实（必须写进方案）**：

> **在全新实例上，`/v1/auth/users/admin` 是免鉴权可调的。**
> 即：**谁能访问到 8848，谁就能抢注管理员账号**。

所以**初始化必须发生在端口暴露之前**，或者初始化完立即确认账号已建。
批次 1 的 compose 如果先把端口映射上去、再慢慢初始化，中间那段窗口就是敞开的。
这与方案 §3.3「各 agent 无法自举」是同一枚硬币的两面——
**该接口存在的意义就是自举，代价就是它必须无鉴权可达。**

2. ✅ YAML 配置无损往返
----------------------

写入含缩进、列表、布尔的 YAML，读回**逐字节一致**。→ 方案 §5「config 用一个 dataId 装 YAML 聚合」可行。

3. ⚠️ 单配置 100KB 上限：写入侧未生效
--------------------------------------

| 内容大小 | 写入 | 读回 |
|---|---|---|
| 90KB | 200 | （该条已被后续删除步骤删掉，未复测） |
| 100KB | 200 | — |
| 101KB | 200 | — |
| **110KB** | **200** | **112640 字节，与写入完全一致** |

**观测**：110KB 可写入且完整读回，「默认 100KB 上限」在此版本 + 此配置下**写入侧不拦**。

**推测（未验证）**：该上限可能是**客户端 SDK 侧**的限制（`defaultMaxSize`），或已被改为可配项。

**对本方案的影响：无**。我们的 prompt 在 1–3KB 量级，离任何上限都很远。**记下来只为纠正文档措辞**——
不要断言「上限 100KB」，应写「实测 110KB 可写入，未撞到上限」。

4. ✅ 版本历史 API 可用，且能取回历史版本的原文
----------------------------------------------

- `GET /v1/cs/history?search=accurate&dataId=&group=&tenant=` 返回 `totalCount` + `pageItems`。
- `GET /v1/cs/history?...&nid=<id>` 能取回**该历史版本的完整 `content`**（实测取回了 `V1_CONTENT`）。
- 历史条目里**带 `md5` 字段**。

**结论**：正文 §6 的「用 `run.started_at` + 版本历史回溯 prompt 内容」**方案成立**——
需要的「当时的内容」确实拿得到，不是只能看到「改过几次」。

5. ⚠️ 「配置不存在」与「namespace 不存在」不可区分
-------------------------------------------------

| 请求 | 响应 |
|---|---|
| 读已删除的配置 | `404` + `config data not exist` |
| 读**根本不存在的 namespace** | `404` + `config data not exist` |

**这是对方案 §5「命名即契约」那条风险的实测坐实**：
dataId 或 namespace 写错一个字，客户端收到的是**与「配置被删」完全相同**的 404。
两者在本方案里走的是同一个降级分支（用快照/默认值），**不会报错、不会有任何提示**，
只会安静地用上旧内容。

→ **强化了读侧校验清单的必要性**：不仅要校验**内容契约**，还应在**启动时**校验
「预期存在的 dataId 是否真的拉到」，拉不到就打 warn/error。否则改名/写错的代价是静默的。

6. ✅ Python 热更新能力（核心结论）
-----------------------------------

**结论：可用。** 外部改动配置后，容器内已注册的监听器**收到了推送回调**，携带新内容：

```
[07:48:10] 初始读取: 'INITIAL'
[07:48:31] >>> 推送回调 <<< data_id=hotupdate.probe content='CHANGED_1'
[07:48:52] >>> 推送回调 <<< data_id=hotupdate.probe content='CHANGED_2'
[07:50:10] 结束：共 2 次推送 -> ['CHANGED_1', 'CHANGED_2']
```

**2 次改动、2 次回调，内容精确，且无重复推送**（Nacos 有重复通知的先例，这次没出现）。
证明这是**服务端推送**而非客户端轮询重读——脚本里除了 `add_listener` 没有做任何拉取。

### ⚠️ 但 API 形态与直觉严重不符，必须记牢

| 项 | 实测 |
|---|---|
| **导入名** | **`v2.nacos`**，**不是 `nacos`** |
| 经典写法 | `import nacos; nacos.NacosClient(...)` 是 **0.x/1.x 老 SDK**；在 3.2.0 上直接 `ModuleNotFoundError: No module named 'nacos'` |
| 调用风格 | **全异步**：`create_config_service()` 是 async 工厂，`get_config` / `add_listener` 均需 `await` |
| 回调签名 | `async def cb(namespace, group, data_id, content)` —— **回调本身也是协程** |
| 底层传输 | **gRPC** → 除 8848 外**必须放通 9848**，否则连不上 |

**这直接影响方案 §4**：`config_center` 的初始化必须在**异步上下文**（FastAPI 的 lifespan）里做。
§4.1 提出的对外接口 `get(key)` 仍可保持**同步零 IO**（读进程内缓存），因为它不碰 SDK——
但**装载/监听那一段是 async 的**，二者要在设计上分清。这一点原方案没写清，需补。

**对我们有利的一点**：v2 SDK 的 `ClientConfigBuilder` 提供 **`cache_dir`** 与 **`load_cache_at_start`**，
即 **SDK 自带本地快照与启动期缓存加载**——正是方案 §4.4「用 SDK 自带快照、不自己再写一层」所假设的能力。
（**尚未实测**其在 Nacos 不可达时是否真能降级启动，列为下一步。）

**尚未验证的**（不带着进批次）：
1. **Nacos 重启后能否自动恢复订阅**（已知 2.0.0~2.0.6 有此缺陷；3.2.0 是否已修，未测）
2. Nacos 不可达时 `load_cache_at_start` 是否真能读到快照并正常启动
3. auth 开启（`username`/`password` 注入 `ClientConfigBuilder`）后监听是否照常

> 时间戳说明：容器内为 UTC（`07:48`），宿主为本地时区（`15:48`），相差 8 小时，非异常。

8. Nacos 重启后能否自动恢复订阅
-------------------------------

**结论（13 次观测后）：失败是**真实的、可复现的、非确定性的**缺陷。**

### 全量观测（auth 开启 + 重启）

| `reconnect_auth_test.sh` | **3 / 5** | ❌0/5、❌0/5、✅5/5、✅5/5、❌0/5 |

| `dual_channel_test.sh` | 0 / 5 | ✅ ×5 |

**同一脚本既有失败也有成功** ⇒ **不是测试脚本的锅**（该假设已被本批反驳）。
失败真实存在，且**不报错**——静默。

### ⚠️ 失败率**不是常数**（未能解释，不得编造归因）

同为「auth 开启 + 重启」，`reconnect_auth_test.sh` 失败率 **60%**，
另两个脚本 **0%**。这不符合"一个固定失败率"的图景。

**已排除的解释**：不是脚本 bug（同脚本内部自相矛盾）。**未查明真实原因。**

**对方案的直接影响（比"有缺陷"更坏）**：
**"在我测过的场景里没复现"不能推出"生产场景里不会发生"。**
因此**任何单一场景的绿灯都不足以作为放行依据**。

> ⚠️ **本节连续写错过两次结论，过程全部留档**（见下）。
> 教训：**单次失败不能证明"必然失败"，单次成功也不能证明"必然成功"。**
> 要断言一个重连行为，**至少要重复若干次**——本目录现有 3 轮，其中 1 轮无效，
> 有效样本只有 2 个，**不足以估出失败率**。

**已确定的部分（三次观测一致，可采信）**：

- ✅ 重启后 `get_config` **仍能读到值** → 连接层是活的，失效**只发生在订阅路径**上
- ✅ 重建 `NacosConfigService` + 重新 `add_listener` **能恢复**（第 3 轮 P2/P3 收到）

→ 即：**失效场景 = 连接可用、订阅可能死、且死不透（有时能自愈）。**
**"有时能自愈"正是必须上主动探针的理由**：不能把可靠性押在一个非确定性的自愈上。

**两轮测试是对称的**（这是结论可信的前提）：监听器存活 240 秒，重启约 40 秒后执行，

### ⚠️ 本节曾写下**错误的结论**，过程留档

第一轮（auth 开启）结论写成「🔴 重启后未恢复、静默失效」。**那个结论是错的，且错法值得记下来**：

**错在测试设计，不在 Nacos。** 回看第一轮原始日志的顺序：

```
[07:55:48] VERDICT 推送次数=0
=== 重启后发布 AFTER_RESTART ===      ← 发布发生在监听器退出**之后**
```

**那 190 秒里，重启之后根本没有任何配置被发布过。** 所以「0 推送」是**必然的**，
与恢不恢复无关。**那次测试没有测到它声称要测的东西。**

> 这条正是我在别处提醒过的坑：**「没观测到」与「观测到没有」不是一回事**。
> 我拿一个空窗口的 0，去下了「静默失效」的结论——**过度归因**。
> 翻案靠的是补测：把发布挪到监听器**存活期内**，结果 5/5 全中。

### 另一处纠正：`-401` 不是鉴权错误码

第一轮我把 `Error [-401]` 读成「鉴权错误码」，据此推断「重连时没重新鉴权」。
**补测推翻了它**：auth **关闭**时，同一条 `-401` 一模一样地出现。

→ `-401` 是**重启窗口内的瞬时断连错误**，与鉴权无关，且**出现几次后自行消失**，
随后连接恢复正常。**不要**再把它解释为鉴权问题。

### 四格全貌

| 组合 | 是否重启 | 结果 |
|---|---|---|
| auth 关闭 | 否 | ✅ 2/2 推送收到 |
| auth 关闭 | **是** | ✅ **5/5 推送收到**（约 20 秒内恢复） |
| auth 开启 | 否 | ✅ 连接与初始读取正常 |
| auth 开启 | **是** | 🔴 **0/5，从未恢复** |

### 机理：**未查明，只有假设**（不许当结论用）

**假设**：重启后连接重建，但客户端**没有重跑登录流程**去换新 token，
于是新连接是未鉴权的，订阅不生效。

**但这条假设与观测有冲突，故不能采信**：`-401` 在 **auth 关闭**时同样出现，
说明它并非 token 被拒。**所以「未重新鉴权」这个解释至少是不完整的。**

→ **成因未查明。** 需要的判别实验（本轮未做）：auth 开启下重启后，
1. 调 `get_config` 是否仍能读到值（区分「整个客户端死了」还是「只有订阅路径坏了」）；
2. 查 Nacos 服务端日志在客户端重连时**有没有收到新的 login 请求**。

**仅凭现有观测，不得写「因为没重新鉴权，所以…」** —— 那是归因，不是观测。

### 一个次要观测：`shutdown()` 在订阅失效后会抛异常

auth 开启那轮结束时：

```
File ".../config_grpc_client_proxy.py", line 254, in close_client
    await self.listen_task
  ...
asyncio.exceptions.CancelledError
```

`shutdown()` 等待 `listen_task` 结束，而该任务卡在 `request_config_server` 上。
**与本节的结论一致**（监听任务处于异常状态），但**不构成独立证据**——
它只说明收尾时任务没在正常循环。记为旁证。

### 对方案的影响（已相应修正）

方案 §4.2 原本写「恢复后 SDK 自动重新订阅」并假设无附加条件。
**实测表明该行为依赖「未开鉴权」，而生产必然开鉴权。** 故：

- **该描述必须加限定条件**，不能无条件保留。
- **自建存活探针从「加固项」重新升格为「必做项」**——但这次的理由是实测的：
  auth 开启下失效是**静默**的，没有任何自动恢复路径。
- ⚠️ 这里牵出一个**需要拍板的权衡**（见 solution.md §9）：
  auth 关闭时重连正常，开启时失效；而 §3.4 又证明了鉴权必须开
  （否则初始化接口无鉴权可达）。**两者目前是冲突的。**

9. ⚠️ `get_config` 的取值路径：**有无监听器不一样**
-------------------------------------------------

**本节的结论直接决定「轮询能不能当兜底」——答案比预想的复杂。**

**实测**（auth 关闭，全新容器无本地快照）：

```
===== 阶段 1：**未注册任何监听器** =====
首读           = 'A0'
外部发布 A1 …
立刻读         = 'A1'      ← ✅ 真去服务端取了

===== 阶段 2：**注册监听器之后** =====
外部发布 A2 …
发布完成，立刻读 = 'A1'      ← ⚠️ 旧值！（服务端此刻已是 A2）
[08:24:57] >>> 推送回调 <<< 'A2'   ← 5 秒后推送把缓存更新了
8 秒后读        = 'A2'
```

**即：同一个 API，有无监听器走的是两条路。**

| 状态 | `get_config` 行为 |
|---|---|
| **无监听器** | **走服务端**——外部发布后立刻能读到新值 |
| **有监听器** | **走本地缓存**——外部发布后立刻读仍是旧值，要等推送更新缓存 |

### 🔴 推论：「有监听器时的轮询兜底」是空的

生产里必然有监听器。那么：

> 监听死掉（订阅失效）→ 本地缓存**停在旧值** → 探针调 `get_config`
> → **返回的仍是那个旧值** → 比对不出差异 → **探针永远认为正常**。

**这是一个"看起来在工作、实际永远发现不了问题"的探针。**
故：**「注册监听器 + 定期 get_config 比对」这个组合不可用。**
（曾据 `sdk_recover_test.py` 那次探针结果推断「get_config 始终可用、可作兜底」——
**那次探针是在监听还活着时调的**，读到的新值其实是推送刚写进缓存的，
**该推断不成立，已作废**。）

### ✅ 但「纯轮询」这条路已验证可行

**不注册任何监听器**时，`get_config` 是服务端取值（阶段 1 已证）。
→ **「彻底放弃监听、只做定期 get_config」是一条干净的保底路径**：
它不依赖任何会坏的东西（不依赖推送、不依赖重连自愈）。
代价：失去即时性，生效延迟 = 轮询间隔。

### ⬜ 仍未验证（下一步）

**监听器死掉之后，`get_config` 会一直读到过期值吗？**
上面的推论是从「有监听器 → 读缓存」推出来的，**但触发条件（监听正常 vs 监听已死）
没有做过对照实验**。差一个实验：auth 开启 → 重启 Nacos 使订阅失效 → 发布新值
→ 反复调 `get_config`，看它是否/何时能读到新值。

- 若**永远读不到** → 推论成立，回到「纯轮询」或「重建 service」
- 若**过一会儿能读到** → 缓存有独立的刷新机制，则「监听 + 轮询」仍可用

**这个实验没做，就不得把上面的推论当作结论写入方案。**

### ⚠️ 测试脚手架自身的一个坑：`curl -o /dev/null` 在本机恒失败

**观测**（同一 URL、同一时刻、同一 curl，仅输出方式不同）：

| 写法 | 退出码 |
|---|---|
| `curl -sf -o /dev/null "$URL"` | **23**（`CURLE_WRITE_ERROR`） |
| `curl -sf "$URL" > /dev/null` | **0** ✅ |
| `curl -sf -o NUL "$URL"` | **0** ✅ |

而同一端点 `http_code=200`（Nacos 也确实 `healthy`）。

**后果**：探活函数若写成 `-o /dev/null`，会**永远返回假**。表现是
「Nacos 明明已经 healthy，脚本却报『未就绪』并中止」——**极易被误读成「Nacos 起不来」**。
（这次就差点写成那个结论，靠 `docker ps` 显示 `Up 4 minutes (healthy)` 才翻案。）

→ **本目录所有脚本的探活一律用 shell 重定向 `> /dev/null`。**
`reconnect_test.sh` 里仍有此写法，**其 `wait_ready` 同样恒假**，引用该脚本前先修。

10. 🔴 SDK 自带快照**不能**用于降级：`load_cache_at_start` 对 config 模块是空操作
--------------------------------------------------------------------------------

**断言 E 的结论：不成立。** 且**归因已到源码级**，不是"没测出来"。

### 先给观测（auth 开、auth 关，各 1 轮，三格）

| 格 | cache_dir | load_cache_at_start | (a) create | (b) get_config |
|---|---|---|---|---|
| P1 造快照（Nacos 在线） | 有 | true | ✅ 0.2s | ✅ `'SNAP_V1'` |
| P2 | **有快照** | **true** | ✅ 9.0s | ❌ 抛异常 |
| P3 | 空 | false | ✅ 9.0s | ❌ 抛异常 |
| P3b | **有快照** | **false** | ✅ 9.0s | ❌ 抛异常 |

三格**一字不差**。异常文本随鉴权变，结果不变：

- auth 开 → `Error [500]: get access token failed`
- auth 关 → `Error [-401]: client not connected,status:RpcClientStatus.UNHEALTHY`

**快照确实落盘**（预注册触发条件 #1，已核）：`<cache_dir>/config/snapshot.probe@@PROMPT@@poc-sp`，
**7 字节**，内容正是 `SNAP_V1`。**触发条件 #1 满足，不是"快照没写出来"。**

### 源码级归因（决定性）

**① `load_cache_at_start` 在 config 模块零引用。** 全仓 `.py` 搜索，该字段的**唯一消费点**是
`naming/cache/service_info_cache.py:28`——**服务发现**模块。config 模块从头到尾没读过它。

→ 即 **`load_cache_at_start=True` 对 `NacosConfigService` 是空操作**。
三格无差异是**必然**，不是实验分辨不出。

**② config 模块的降级路径存在，但被 `error_code == 400` 卡死。**
`config/nacos_config_service.py:39` 的 `get_config`：

```python
content, _ = await self.config_info_cache.get_fail_over_config_cache(...)   # 先读 failover
if not content:
    try:
        content, _ = await self.grpc_client_proxy.query_config(...)
    except NacosException as e:
        if e.error_code == 400:                      # ← 只有「配置不存在」才降级
            ...
            return await self.config_info_cache.get_config_cache(...)   # 读本地快照
        raise e                                      # ← 连不上 / 鉴权失败：直接抛
```

我们的 error_code 是 **500**（auth 开）与 **-401**（auth 关），**都不等于 400 → 一律 `raise e`**。
本地快照文件明明就在盘上，**读不到它**。

**③ `_failover` 缓存**（`<key>_failover` 文件，人工覆盖用）在**查服务端之前**就读，
一旦存在就**永远压过服务端**，热更新会失效 → **不能当降级通道**。

### 对方案的影响

- **§4.4「用 SDK 自带快照、不自己再写一层」作废**，必须补自建快照层。
- 但**不必整个换掉**：SDK 在每次成功读取时**已经把内容写到** `<cache_dir>/config/<cache_key>`
  （P1 读一次即落盘，已核）。所以最小改法是——
  **我们自己 `try get_config / except 再读那个文件`**，格式是裸文本，无需解析。
- **必须用自建层兜住的三类 error_code**：`-401`（连不上）、`400` 之外的连接类、
  以及 auth 换 token 失败的 `500`。**不能只兜连接失败**。

### ⚠️ 本节推翻了预注册里的一条触发条件（方法论，须记）

预注册写「**P2 与 P3 必须出现差异**，否则无判别力」。本轮三格全同 → 按字面应记「无效轮」。

**但那条触发条件是为"假阳性"设计的**（防止"两格都成功"时把功劳归给快照）。
它没覆盖「**三格都失败、且失败原因已由源码解释**」这种情况——
此时"无差异"**恰恰是结论本身**，记"无效轮"会把一条已经钉死的结论丢掉。

→ **规则不改，但记例外**：当**源码级证据**能解释"为何必然无差异"时，
观测可**降格采信为观测**，并**同时保留**"对 E 的预注册判定为无效轮"的原始记录。
**不得**因为结论看起来对就静默放宽规则——这正是本文件存在的原因。

**方法教训**：断言 E 真正该写的触发条件是
「**失败必须发生在快照路径之后才作数**」——本轮失败发生在**网络/鉴权层**，
根本到不了快照路径。与 C、D 犯的是同一类错：**前提条件没写在判据里**。

11. 🔴 运行中的实例遇 Nacos 宕机：`get_config` 同样取不到值（断言 F 不成立）

**动机**：原方案 §9 风险表写「Nacos 挂了 → 本地快照降级 → **已运行的实例不受影响**」。
该句从未验证，且**与 §10 不是一回事**：§10 测**启动期**（Nacos 先挂、进程后起），
本节测**运行期**（进程先起并读到值、Nacos 后挂）。

**观测**（auth 开启，2 轮；此处记第 1 轮，两轮一致）：

```
[04:04:05] t=  0.0s get_config='RUN_V1'     ← 连着呢
[04:04:10] t=  5.0s get_config='RUN_V1'
[04:04:15] t= 10.1s get_config='RUN_V1'
[04:04:20] t= 15.1s get_config='RUN_V1'
        ← t≈20s 停 Nacos
[04:04:25] t= 20.1s get_config 异常 NacosException: Error [-401]:
                    client not connected,status:RpcClientStatus.UNHEALTHY
  …此后每 5 秒一次，直到 t=67.9s，**全部抛同一个异常**
[04:05:18] VERDICT 成功=4 异常=10
```

**触发条件自检（预注册要求的两条都满足）**：
① 宕机前确实读到过值（4 次 `RUN_V1`）；② 客户端确实察觉断连（日志 37 条 `failed to connect`/`UNHEALTHY`）。

→ **结论：F 不成立。** 一旦断连，SDK 的 `get_config` **立刻转为抛异常，一次都没能从内存兜住**。
"已运行的实例不受影响"这句**对 SDK 而言是错的**。

### ⚠️ 但这条证伪的是 SDK，**不是**"应用不受影响"（不许外推）

本节测的是 **SDK 的 `get_config`**。生产里业务代码若像原方案 §4.1 设想的那样
**把配置读进自己的进程内存**（启动时读一次，之后 `get(key)` 零 IO），
那就**根本不会每请求都调 `get_config`** → 那种形态下"实例不受影响"**仍可能是对的**。
本节既没有证明、也没有证伪它——**未测**。

### 与 §10 的关系

§10 的成因（`if e.error_code == 400` 才降级，`-401` 直接抛）**完全解释了本节**：
`-401` 不在降级分支里。两节是同一枚硬币的两面，不是两个独立缺陷。
